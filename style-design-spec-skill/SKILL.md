# Skill：目标软件 / 网站 / 风格设计规范采集与生成

## 1. Skill 定位

本 Skill 用于在用户明确要求整理、提取、分析或生成某个软件、网站、应用或设计风格的设计规范时触发。

该 Skill 的核心任务不是泛泛地生成一套“好看的 UI 风格”，而是基于目标对象的真实页面、真实界面、真实交互和可观察设计数据，整理出一份可以指导后续软件开发设计、AI Coding、前端实现和页面验收的设计规范。

最终输出应形成完整闭环：

1. `design-spec.md`：完整设计规范
2. `design-tokens.md`：面向代码实现的设计变量
3. `design-review-checklist.md`：页面开发后的设计一致性检查清单

---

## 2. 触发条件

只有在用户明确表达以下意图时，才允许触发本 Skill：

1. 用户明确要求“整理设计规范”
2. 用户明确要求“提取设计规范”
3. 用户明确要求“分析某个软件 / 网站 / App / 小程序的 UI 风格”
4. 用户明确要求“根据某个参考对象生成设计规范”
5. 用户明确要求“把某个风格转化为可执行的设计规范”
6. 用户明确要求“为后续 AI Coding 生成设计规范”
7. 用户明确要求“根据某个成品页面生成 design-spec / design-tokens / review-checklist”

典型触发表达：

```text
帮我整理这个网站的设计规范。
参考这个 App，生成一套设计规范。
把 Linear 风格整理成 AI Coding 可以用的设计规范。
分析这个 PC 软件的界面，并输出设计规范。
基于这个官网，生成 design-spec.md、design-tokens.md 和 design-review-checklist.md。
```

---

## 3. 不触发场景

以下场景不得自动触发本 Skill：

1. 用户只是说“页面做得高级一点”
2. 用户只是说“风格简洁一些”
3. 用户只是要求优化单个页面布局
4. 用户只是要求生成一个普通 UI 页面
5. 用户只是要求写前端代码
6. 用户只是要求推荐设计风格
7. 用户只是询问某种风格是什么
8. 用户没有明确要求整理、提取或生成设计规范

示例：

```text
帮我把这个页面做得好看一点。
这个页面风格怪怪的，帮我优化。
帮我写一个后台管理页面。
我想要一个科技感风格。
```

遇到这些情况时，应只按照用户当前需求进行页面优化、解释或开发建议，不应自动进入完整设计规范采集流程。

## 4. 目标对象范围

目标对象可以是：

- 某个具体网站
- 某个 Web 应用
- 某个 PC 客户端软件
- 某个移动端 App
- 某个小程序
- 某个设计系统
- 某类明确的视觉风格
- 某个品牌官网或产品官网

例如：

```text
请帮我整理 Linear 官网的设计规范。
请分析 Notion 的产品风格，并生成一份设计规范。
请参考飞书后台管理系统，整理一套企业级 SaaS 设计规范。
请根据某个 PC 软件的界面，提取它的设计规范。
```

## 5. 数据真实性原则

执行本 Skill 时，必须严格基于目标软件、网站、应用或风格的真实页面数据进行分析和输出。

禁止：

1. 凭空编造设计规范
2. 只根据“某某风格”这个名称进行主观想象
3. 使用宽泛、模糊、无法落地的描述代替真实页面数据
4. 未说明来源就给出精确色值、字号、间距
5. 把通用 UI 规范包装成目标软件的专属设计规范

设计规范中的以下内容必须尽量来自实际页面观察：

- 色彩
- 字号
- 字重
- 间距
- 圆角
- 阴影
- 边框
- 布局
- 导航结构
- 组件样式
- 表格样式
- 表单样式
- 按钮样式
- 卡片样式
- 弹窗样式
- 空状态
- 加载状态
- 交互反馈
- 动效表现
- 响应式规则
- 页面尺寸适配
- 按钮和触控区域尺寸
- 文字遮挡、重叠、挤压与异常截断
- hover / active / selected 边框与背景颜色协调性

如果无法获得精确数值，需要明确标注为“基于页面观察的近似值”，不得伪装成精确测量结果。

正确示例：

```text
按钮圆角约为 8px，基于页面截图观察估算。
```

错误示例：

```text
按钮圆角为 8px。
```

优先采集以下页面：

1. 首页
2. 产品页
3. 定价页
4. 登录页
5. 注册页
6. 控制台页面
7. Dashboard 页面
8. 列表页
9. 详情页
10. 设置页
11. 帮助文档或设计系统页面

采集重点：

- 页面整体布局
- 首屏结构
- 导航方式
- 色彩体系
- 字体层级
- 按钮样式
- 卡片样式
- 表格样式
- 表单样式
- 图标风格
- 动效风格
- 空状态设计
- 响应式表现

如果某些页面需要登录、付费、邀请权限或企业账号才能访问，需要在输出中明确说明：

```text
该页面需要登录或权限，当前无法直接访问，因此无法完整采集控制台内部设计数据。
```

此时应提示用户提供：

- 测试账号

## 9. 风格类目标采集要求

当用户指定的是某种风格，而不是具体软件或网站时，例如：

- 高级灰商务风
- 暗黑科技风
- 日式极简风
- 企业级 SaaS 风
- 苹果官网风
- Linear 风
- Notion 风

应优先寻找该风格下的代表性网站、产品官网、公开设计系统或成熟案例进行观察。

输出时必须说明参考来源。

示例：

```text
本次规范基于以下参考对象整理：
1. Linear 官网
2. Vercel 官网
3. Raycast 官网
4. 同类 SaaS 产品控制台公开截图
```

如果缺少足够明确的参考来源，应根据用户目标项目类型选择合理参考对象，但必须在文档中标注：

```text
由于用户未指定具体参考产品，本规范基于目标风格关键词和同类公开案例进行归纳，具体数值为近似建议。
```

## 10. 工作流程

### Step 1：判断是否触发 Skill

先判断用户是否明确要求整理、提取、分析或生成某个软件、网站、应用或风格的设计规范。

如果用户只是要求页面优化、写代码、做 UI、推荐风格，不触发本 Skill。

---

### Step 2：确认目标对象类型

将目标对象归类为：

1. 网站 / 官网
2. Web 应用
3. PC 客户端软件
4. 移动端 App
5. 小程序
6. 设计系统
7. 抽象风格
8. 品牌或产品官网

不同对象采用不同的数据采集方式。

---

### Step 3：采集真实页面数据

根据目标对象，尽可能打开并观察真实页面、真实应用或真实截图 / 视频。

采集数据时应记录：

1. 数据来源
2. 页面名称
3. 可观察结论
4. 估算值
5. 无法采集的内容
6. 需要用户补充的材料

---

### Step 4：区分三类结论

生成设计规范时，必须区分三类内容。

#### 4.1 真实采集结论

来自目标页面、截图、视频、应用界面的直接观察。

示例：

```text
目标网站首页大量使用白色背景、黑色主标题和低饱和灰色说明文字。
```

#### 4.2 观察估算值

来自视觉观察，但没有工具精确测量。

示例：

```text
卡片圆角约为 12px，基于截图观察估算。
```

#### 4.3 适配建议

为了让该风格适合用户当前项目而做出的设计转化。

示例：

```text
由于当前项目是企业级 OA 系统，建议在保留目标风格克制视觉的同时，提高表格密度和操作区清晰度。
```

输出时不得混淆这三类内容。

---

### Step 5：生成三份核心文档

当信息充足时，本 Skill 最终输出：

```text
/docs/design/design-spec.md
/docs/design/design-tokens.md
/docs/design/design-review-checklist.md
```

如果存在无法采集的数据，必须在对应位置标注：

```text
该项因缺少目标页面数据，暂无法准确提取。
```

或：

```text
该项为基于现有截图的观察估算值。
```

## 11. 输出物一：design-spec.md

`design-spec.md` 是完整设计规范文档，用于说明目标风格的设计定位、视觉规则、组件规范、页面模板、交互规范和前端实现建议。

### 11.1 文档结构

```markdown
# XXX 设计规范

## 1. 采集说明
## 2. 参考来源
## 3. 风格定位
## 4. 设计原则
## 5. 色彩系统
## 6. 字体系统
## 7. 间距系统
## 8. 圆角系统
## 9. 阴影系统
## 10. 边框规范
## 11. 布局规范
## 12. 组件规范
## 13. 页面模板规范
## 14. 交互规范
## 15. 动效规范
## 16. 响应式规范
## 17. 前端实现建议
## 18. AI Coding 执行提示词
## 19. 无法采集项说明
```

### 11.2 采集说明

必须说明：

- 目标对象
- 目标对象类型
- 采集方式
- 已采集页面
- 未能采集页面
- 数据可信度
- 是否存在估算值

示例：

```text
目标对象：Linear 官网
目标对象类型：网站 / SaaS 产品官网
采集方式：公开页面观察
已采集页面：首页、产品页、定价页、登录页
未能采集页面：登录后的控制台页面
数据可信度：公开页面视觉观察，部分尺寸为近似估算
```

### 11.3 参考来源

列出所有参考页面、截图、录屏、应用界面或设计系统来源。

### 11.4 风格定位

说明该风格给用户的整体感受，例如：

- 克制
- 高级
- 科技
- 专业
- 轻量
- 可信
- 清晰
- 企业级
- 数据驱动

并说明这种气质如何体现在界面中。

### 11.5 色彩系统

必须包含：

```text
主色：
- 用途：主按钮、关键操作、激活状态、重点信息
- 推荐色值：#xxxxxx
- 数据来源：真实采集 / 观察估算 / 适配建议

辅助色：
- 用途：次级按钮、辅助图标、弱强调区域
- 推荐色值：#xxxxxx
- 数据来源：真实采集 / 观察估算 / 适配建议

背景色：
- 页面背景色
- 卡片背景色
- 弹窗背景色
- 侧边栏背景色

文本色：
- 一级标题
- 正文
- 次级说明
- 禁用文字

状态色：
- 成功
- 警告
- 错误
- 信息

边框色：
- 默认边框
- 弱边框
- 激活边框
- 分割线颜色
```

### 11.6 字体系统

必须包含：

```text
字体家族：
- 中文：推荐系统字体或指定字体
- 英文：推荐系统字体或指定字体

字号层级：
- 页面主标题：xx px
- 模块标题：xx px
- 正文：xx px
- 辅助说明：xx px
- 表格文字：xx px
- 按钮文字：xx px

字重：
- 标题：600 / 700
- 正文：400 / 500
- 辅助文字：400

说明：
- 标注真实采集 / 观察估算 / 适配建议
```

### 11.7 间距系统

必须包含：

```text
基础单位：4px 或 8px

推荐间距：
- 页面外边距：24px / 32px
- 模块间距：24px
- 卡片内边距：16px / 20px / 24px
- 表单项间距：12px / 16px
- 按钮内边距：8px 16px
- 表格单元格内边距：12px 16px

说明：
- 标注真实采集 / 观察估算 / 适配建议
```

### 11.8 圆角系统

必须包含：

```text
小圆角：4px，用于 Tag、小按钮、轻量输入框
中圆角：8px，用于按钮、输入框、普通卡片
大圆角：12px / 16px，用于重点卡片、大模块、弹窗
说明：标注真实采集 / 观察估算 / 适配建议
```

### 11.9 阴影与边框规范

必须包含：

```text
边框：
- 默认边框：1px solid #E5E7EB
- 弱边框：#F0F0F0
- 激活边框：主色或强调色

阴影：
- 默认卡片尽量少用强阴影
- 悬浮卡片可使用轻微阴影
- 弹窗可使用中等阴影
- 避免大量使用厚重投影
```

### 11.10 组件规范

至少覆盖以下组件：

1. Button 按钮
2. Input 输入框
3. Select 选择器
4. Table 表格
5. Card 卡片
6. Modal 弹窗
7. Drawer 抽屉
8. Tabs 标签页
9. Tag 标签
10. Alert 提示
11. Empty 空状态
12. Loading 加载态
13. Sidebar 侧边栏
14. Topbar 顶部栏
15. Form 表单
16. Dashboard 指标卡

每个组件需要说明：

```text
组件名称：
- 使用场景
- 默认样式
- 尺寸
- 最小点击 / 触控区域
- 颜色
- hover / active / selected 边框与背景颜色
- 交互状态
- 禁用状态
- 文本溢出、换行、省略和防重叠规则
- 数据来源：真实采集 / 观察估算 / 适配建议
- 开发实现建议
```

### 11.11 页面模板规范

根据目标项目类型，生成常见页面模板。

例如企业级 SaaS / OA 系统可以输出：

1. 登录页
2. 首页 Dashboard
3. 列表管理页
4. 详情页
5. 表单创建页
6. 审批流程页
7. 工单处理页
8. 数据分析页
9. 设置页
10. 个人中心页

每个页面需要说明：

```text
页面名称：
- 页面用途
- 推荐布局
- 核心组件
- 信息层级
- 操作区位置
- 数据来源：真实采集 / 观察估算 / 适配建议
- 开发注意事项
```

## 12. 输出物二：design-tokens.md

`design-tokens.md` 是面向 AI Coding 和前端开发的设计变量文档。

该文档必须把 `design-spec.md` 中的设计结论转化为明确 token，避免后续开发过程中随意写颜色、字号、间距和圆角。

### 12.1 文档结构

```markdown
# Design Tokens

## 1. Token 来源说明
## 2. Color Tokens
## 3. Typography Tokens
## 4. Spacing Tokens
## 5. Radius Tokens
## 6. Shadow Tokens
## 7. Border Tokens
## 8. Z-Index Tokens
## 9. Motion Tokens
## 10. Breakpoint Tokens
## 11. Tailwind CSS 配置建议
## 12. CSS Variables 建议
## 13. 无法确认的 Token
```

### 12.2 Token 来源说明

必须说明 token 的来源：

- 真实采集
- 观察估算
- 项目适配建议

### 12.3 Color Tokens

必须输出：

```text
--color-primary
--color-primary-hover
--color-primary-active
--color-primary-light
```

## 13. 输出物三：design-review-checklist.md

```markdown
## 4. 字体检查
```

```text
[ ] 页面设计是否基于真实采集数据？

[ ] 是否区分了真实采集、观察估算和适配建议？
```

## 14. 无法访问目标对象时的处理方式

如果无法访问目标软件、网站、App 或关键页面，应暂停完整规范生成，并明确说明缺失信息。

需要向用户说明：

1. 当前无法访问的对象是什么
2. 因为什么原因无法采集
3. 还缺少哪些页面或操作数据
4. 用户可以提供哪些材料
5. 当前最多只能做哪种程度的分析

标准回复格式：

```text
当前无法完整采集该目标对象的真实界面数据，因此不能直接生成完整设计规范。

缺失内容：
- 无法访问控制台页面
- 无法打开 PC 客户端
- 无法进入移动端 App 内部页面

请提供以下任意材料：
- 测试账号
- 关键页面截图
- 操作录屏
- 软件安装包
- App 安装包
- 产品演示视频
- Figma / Sketch / MasterGo 设计稿

拿到这些材料后，我可以继续整理：
1. design-spec.md
2. design-tokens.md
3. design-review-checklist.md
```

```text
请严格按照 design-spec.md、design-tokens.md 和 design-review-checklist.md 进行页面开发。

要求：

1. 所有页面必须使用统一色彩、字号、间距、圆角、阴影和组件规范。
```

## 17. 使用原则总结

1. 本 Skill 仅在用户明确要求整理某个软件、网站、应用或风格的设计规范时触发。
2. 本 Skill 不用于普通页面优化、普通 UI 生成或普通代码开发。
3. 所有设计结论都应尽量来自参考页面、真实应用、截图、视频或设计稿的观察与归纳。
4. PC 应用和移动端应用必须尽可能实际打开采集；无法打开时必须要求用户提供权限、截图或操作视频。
5. 不直接复制目标品牌的 Logo、商标、插画或专有视觉资产。
6. 可以学习设计规律，但必须转化为适合当前项目的独立设计系统。
7. `design-spec.md` 负责说明设计规则。
8. `design-tokens.md` 负责把设计规则转化为代码变量。
9. `design-review-checklist.md` 负责开发完成后的设计一致性检查。
10. 三份文档必须保持一致，不能出现 token 与设计规范冲突的情况。
11. 后续任何页面开发、组件新增、样式调整，都必须同时参考这三份文档。
