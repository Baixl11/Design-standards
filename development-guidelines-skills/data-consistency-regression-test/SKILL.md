# 数据一致性与回归测试 Skill

## 目标

在需求变更、问题修复、页面修改、字段调整、接口调整之后，检查修改是否真正覆盖所有影响范围，避免出现：

```text
1. 当前页面改了，其他页面没改。
2. UI 改了，底层数据源没改。
3. 类型改了，mock 没改。
4. 接口改了，调用页面没改。
5. 枚举改了，筛选/统计/导出没改。
6. 数据展示对了，但测试和文档没同步。
```

## 触发场景

当以下动作完成后必须触发：

```text
1. 需求变更修改完成
2. bug 修复完成
3. 字段/枚举/接口修改完成
4. 页面展示调整完成
5. 表格/表单/筛选/统计调整完成
6. 数据源重构完成
7. 组件抽取或复用调整完成
8. 后端接口或数据库结构调整完成
```

## 检查前提

执行前应读取或参考：

```text
1. 本次需求变更说明
2. change-impact-analysis 输出的影响范围清单
3. 项目开发规范
4. 数据源地图 docs/data-source-map.md
5. 实际修改文件列表
```

## 核心检查流程

### 1. 修改项完成度检查

```text
1. 用户提出的原始修改点是否全部完成？
2. 是否存在只完成表面 UI、未完成业务逻辑的情况？
3. 是否存在只修改一个入口、其他入口未同步的情况？
4. 是否存在未处理的异常状态、空状态、加载状态？
```

### 2. 影响项同步检查

逐项核对影响范围清单：

```text
页面是否同步
组件是否同步
类型是否同步
常量/枚举是否同步
service/API 是否同步
store/state 是否同步
hook/composable/provider 是否同步
mock 数据是否同步
测试是否同步
文档是否同步
```

### 3. 数据源一致性检查

必须确认：

```text
1. 是否仍然只有一个权威数据源？
2. 是否新增了重复数据定义？
3. 是否存在页面本地硬编码业务字段？
4. 类型定义与 mock 是否一致？
5. mock 与真实接口结构是否一致？
6. 状态枚举与显示文案是否一致？
7. 前端类型与后端 DTO/schema 是否一致？
```

### 4. 关联页面检查

如果本次修改涉及共享数据，必须检查：

```text
1. 列表页
2. 详情页
3. 新增/编辑表单页
4. 首页/仪表盘统计
5. 筛选面板
6. 导出功能
7. 权限菜单
8. 弹窗/抽屉/侧边栏
9. 移动端适配页面
10. 打印/报表页面
```

### 5. 功能回归检查

至少覆盖：

```text
1. 正常数据展示
2. 空数据展示
3. 加载中状态
4. 接口错误状态
5. 无权限状态
6. 筛选/排序/分页
7. 新增/编辑/删除
8. 导入/导出
9. 刷新/返回/路由跳转
10. 本地缓存/状态恢复
```

### 6. 测试用例检查

根据项目类型检查：

```text
前端：组件测试、页面测试、E2E 测试
后端：单元测试、接口测试、数据库迁移测试
移动端：Widget 测试、集成测试、权限测试
桌面端：IPC 测试、本地文件测试、窗口行为测试
```

如果无法实际运行测试，必须说明：

```text
未运行测试的原因
建议用户本地执行的测试命令
需要人工检查的页面或流程
```

## 强制约束

```text
1. 不能只说“已修改完成”，必须说明检查了哪些影响项。
2. 如果无法确认底层数据是否同步，必须明确标记为“需人工复核”。
3. 如果发现重复数据源，必须建议回到统一数据源规范进行重构。
4. 如果发现其他页面未同步，必须退回 change-impact-analysis 重新修改。
5. 如果测试未运行，必须给出用户可复制执行的测试命令。
```
